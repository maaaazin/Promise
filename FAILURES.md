## Known gotchas to watch for (not yet happened — preventive)
- CopilotKit runtime endpoint path must match exactly between the frontend provider config and `/app/api/copilotkit/route.ts` — a silent mismatch just looks like "the sidebar doesn't respond," no clear error.
- OpenAI structured outputs (`response_format: json_schema`) fail silently or throw opaque errors if the schema has extra/missing `required` fields — validate the schema against the SDK version actually installed before assuming the extraction prompt is wrong.
- `lowdb` v3+ is ESM-only and can conflict with a CommonJS-configured Next.js setup — if using it, confirm import style works before building on top of it.
- Slack incoming webhooks require `Content-Type: application/json` and reject overly large payloads — test with a raw `curl` call before wiring it into the approval flow, so a UI bug and a webhook bug don't get debugged as one problem.
- Next.js: any env var prefixed `NEXT_PUBLIC_` is exposed to the browser. Never prefix `OPENAI_API_KEY` or `SLACK_WEBHOOK_URL` that way — check this explicitly, it's an easy silent security mistake, not just a bug.
- `useCopilotAction` HITL render props have changed across CopilotKit versions — check the installed version's docs/types before writing the approval card, don't assume an API shape from memory.

```

```
The HTTP response itself was a clean `400 {"error":"invalid_request","message":"Missing method field"}` (correctly rejecting my malformed test payload before the GraphQL layer even ran) — but the OpenAI client instantiation still fired eagerly server-side and threw as an **unhandled promise rejection** in the server console, separate from the HTTP response.
Root cause: `OpenAIAdapter`'s constructor defers creating the underlying `OpenAI` client until `getLanguageModel()`/`ensureOpenAI()` is called, which happens as soon as `CopilotRuntime.handleServiceAdapter(serviceAdapter)` touches the adapter during request setup — this runs regardless of whether the request body is otherwise valid, and with no `OPENAI_API_KEY` in the environment, the OpenAI SDK's own constructor throws synchronously inside an async path that isn't wrapped in a try/catch by the runtime, so it surfaces as an unhandled rejection rather than a caught, client-facing error.
Fix: None needed in our code — this is expected, correct behavior for a missing key (confirmed intentional per DATA_SPEC.md's env table: "extraction/drafting hard-fail without it"). Not fixed, just confirmed and documented so the next session doesn't mistake these console errors for a bug in the new route. Resolves itself once a real `OPENAI_API_KEY` is added to `.env.local` — that is the actual blocker, tracked separately, not a code defect.
Time lost: ~5 min (spent confirming this was expected-given-no-key rather than a routing bug).

### [12:50] Correction to the entry above: "Missing method field" is not a GraphQL pre-check — this runtime speaks AG-UI, not GraphQL, at all
Attempted: With a real `OPENAI_API_KEY` finally in `.env.local`, tried to verify the CopilotKit wiring end-to-end without a browser (none available in this environment) by hand-sending a classic GraphQL `generateCopilotResponse` mutation — the protocol `@copilotkit/runtime-client-gql`'s `CopilotRuntimeClient` and the runtime README's older examples describe — directly to `/api/copilotkit`, using the SDK's own real generated query document (not hand-typed).
Error (paste exact text, don't paraphrase):
```
HTTP status: 400
RAW BODY:
 {"error":"invalid_request","message":"Missing method field"}
```
Root cause: the installed `@copilotkit/runtime@1.71.1` has removed GraphQL serving entirely (confirmed via `@copilotkit/runtime`'s own doc comment: "Nothing in this package serves GraphQL any more -- every v1 integration entry point delegates to the v2 Hono endpoint"). `copilotRuntimeNextJSAppRouterEndpoint` mounts a single-route Hono handler (`src/v2/runtime/endpoints/single-route-helpers.mjs`) that only understands a `{method, params, body}` JSON envelope with a fixed method whitelist (`agent/run`, `agent/suggest`, `agent/connect`, `agent/stop`, `info`, `inspector/metadata`, `inspector/learning`, `transcribe`, `resource/request`) — there is no GraphQL method in that list, so any GraphQL-shaped POST body is rejected as "missing method field" regardless of how well-formed the GraphQL itself is. Last task's entry above mis-described this exact response as "correctly rejecting my malformed test payload before the GraphQL layer even ran" — there is no GraphQL layer to run; that framing was wrong, corrected here.
Fix: Not a fix to the app — **the shipped code in `app/api/copilotkit/route.ts`, `app/layout.tsx`, and `app/page.tsx` was never touched and needed no change.** `@copilotkit/react-core`'s actual `<CopilotKit>` provider already speaks this same envelope protocol internally (confirmed by reading its compiled source: it negotiates `runtimeTransport: "single" | "rest" | "auto"`, defaulting to `"auto"`). The mismatch was only in my own verification script, which assumed the older documented GraphQL wire format. Corrected the script to send `{method: "agent/run", params: {agentId: "default"}, body: <AG-UI RunAgentInput>}` — `"default"` because `CopilotRuntime.handleServiceAdapter()` auto-registers a `BuiltInAgent` under that exact name when no explicit `agents` list is configured and the service adapter exposes a language model (true for our plain `OpenAIAdapter` setup) — confirmed by reading `handleServiceAdapter`'s source, not assumed. Validated the corrected request body against the real exported `RunAgentInputSchema` (from `@ag-ui/core`) before sending, so a subsequent failure would be the server's, not a self-inflicted malformed request. That corrected request succeeded end-to-end (see verification report) — real evidence the actual app wiring is correct.
Time lost: ~35 min (reading `single-route-helpers.mjs`, `fetch-handler.mjs`, `handle-run.mjs`, `copilot-runtime.mjs`, and `@ag-ui/core`'s schema to reconstruct the real protocol from source rather than guessing).

### [13:20] In-memory radar state silently reset mid-verification when a new route was compiled
Attempted: After confirming `advanceClock` auto-flagged and auto-drafted `c-maya-0` (score 32→73) via `/api/radar`, hit `/api/copilotkit` for the first time in this dev session (to wire-protocol-verify the auto-nudge). Then, moments later, called `/api/radar` again to approve `c-maya-0`.
Error (paste exact text, don't paraphrase): No thrown error — the approve call returned a clean `200` with `delivered:true`, but the returned state showed `c-maya-0` back at `riskScore: 32, status: "tracked"` (its cold-start value) instead of the `73, "flagged"` it held a minute earlier, `now` had reset to the original `2026-09-12T10:00:00.000Z` instead of the advanced date, and the dev log showed a second, unprompted `[store] extraction: live — 6 commitment(s) extracted from 12 seed messages` line that nothing in my request should have triggered.
Root cause: Next.js dev mode compiles each API route as its own on-demand bundle and can dispose/recompile a route's module graph after a period of no requests to it (here, `/api/radar` sat idle while `/api/copilotkit` compiled for the first time — that compile alone took ~10s, plus script setup time around it). `lib/store.ts` keeps all radar state in a single module-level `statePromise` variable with no persistence, so a recompiled module graph is a fully reset store — this is inherent to the "in-memory or lowdb only" data-layer decision in ARCHITECTURE.md, not a bug introduced by this task's changes.
Fix: Not fixed (data layer is out of scope — ARCHITECTURE.md forbids adding persistence). Re-ran the full advance→auto-flag→auto-draft→approve sequence back-to-back with no idle gap (and no intervening first-time route compile) and got a clean, internally-consistent result the second time — see BUILD_PLAN.md phase 3 notes. **Demo-day implication:** do the full 5-step demo run as one continuous take; avoid long pauses between "simulate time" and "approve," and make sure `/api/copilotkit` has already been hit once (e.g. by opening the sidebar) before relying on state that was set up via `/api/radar` alone.
Time lost: ~10 min (diagnosing why a second live extraction log line appeared and why scores had reverted, before realizing it was dev-server route recompilation rather than a logic bug in the new auto-flag code).

### [14:07] RUN_ERROR: "Tool result is missing for tool call ..." after two commitments auto-flagged at once
Attempted: First real browser session of the build. Advanced the mock clock once and watched two commitments cross the risk threshold simultaneously (Maya at 73, Jordan Ellis at 77). CopilotKit's AG-UI Events devtools panel showed a clean tool call and `RUN_FINISHED` at 14:07:39, then a second `RUN_STARTED` at 14:07:57 that immediately errored.
Error (paste exact text, don't paraphrase):
```
RUN_ERROR: Tool result is missing for tool call call_eNiFyA05ZoQwUgRguEM0ZGEo.
```
Root cause: `nudgeAutoFlagged()` in `app/page.tsx` already restricted itself to nudging only the single riskiest newly-flagged commitment per call (a teammate's earlier fix, commit `098de10`) — so the bug is not a same-call loop sending multiple `appendMessage`s without awaiting resolution, that pattern no longer exists. Confirmed instead, via the exact AG-UI wire-protocol technique from prior rounds: reconstructed a thread where one nudge's `approveEscalation` tool call was left unresolved (no tool-result message) and a second, independent nudge call (`nudgeApproval`) appended a new user message into that same thread — this reproduced the identical error verbatim. AG-UI requires a pending tool call's result before a thread accepts a new message; nothing in the code tracked whether a previously-sent nudge's tool call was still awaiting a human's Approve/Dismiss click, so any second invocation of `nudgeApproval` (from a second "Simulate 3 days passing" click, an LLM-invoked `recomputeRisk`, or the second of two commitments crossing in one call once naively un-restricted) could fire while the first was still pending. Ruled out React StrictMode/dev double-invoke as an alternative cause: `nudgeAutoFlagged` is only ever called from event-handler bodies (`handleAdvance`, the `recomputeRisk` action handler), never from a `useEffect` or a component render body or a `useState` updater function — the only call sites StrictMode double-invokes in dev — and no `reactStrictMode` override exists anywhere in the project (verified: no `next.config.*` file at all).
Fix: Centralized all nudge-sending behind `nudgeApproval()` in `app/page.tsx`, now backed by a `pendingNudgeIdRef` + `nudgeQueueRef` (via `useRef`): a nudge is sent immediately only if none is currently pending; otherwise it's queued. `resolveNudge()` is called from the `approveEscalation` card's `onApprove` and from `handleDismiss` (shared by manual dismiss and the `dismissFlag` action) to clear the pending ref and release the next queued nudge. `nudgeAutoFlagged` now simply queues every newly-flagged commitment (riskiest first) instead of picking only one — the queue guarantees at most one is ever in flight, so none are silently dropped. Chose this (option a from the task) over batching all newly-flagged commitments into one message (option b) because option b alone would not close the actual race: the confirmed root cause is *overlapping separate invocations* of `nudgeApproval`, not a same-call loop, so only a persistent pending/queue gate — not a bigger single message — prevents it regardless of trigger source.
Verified: (1) wire-protocol reproduction of the raw bug, reconstructing the exact `RUN_ERROR` text from a live run against real flagged commitments; (2) a logic-level simulation of the exact queueing functions (copied verbatim, `appendMessage` mocked) proving that with Maya (73) and Jordan (77) both newly flagged in one call, only one `appendMessage` fires immediately (Jordan, riskier), a duplicate/overlapping nudge for the same pending commitment is suppressed, and Maya's queued nudge fires only after `resolveNudge` runs — both reachable, neither dropped, and the single-commitment case is provably unchanged; (3) wire-protocol confirmation that once a nudge's tool call carries a proper tool-result message, the runtime accepts the next nudge on the same thread with no `RUN_ERROR`, and `gpt-4o` correctly emits a second `approveEscalation` call with Maya's own commitmentId and draft.
Time lost: ~40 min (tracing the actual current `nudgeAutoFlagged` implementation before trusting the task's stated hypothesis, since the same-call-loop pattern it described had already been removed by an earlier commit; reconstructing the wire-protocol repro to get real proof rather than a plausible-sounding story).
